# SNS安定化・投稿担当への共有（2026-10-31）

## 2026-11-02 配信障害と起動遅延の分離・独立した起動経路

- SNS監視は媒体別の未処理・結果不明・鮮度切れで失敗する。GitHubのscheduleが90分超空いた場合はSCHEDULER_DELAYとして独立表示し、配信完了やフィード保留と混同しない。保護停止・deferredは未完了のまま表示する。
- 監視で安全なready記事が見つかり、実行中・待機中の配信がなく、直近の起動から10分以上経過したときは、既存social-publish.ymlを1回だけ起動する。投稿承認・媒体選択・台帳は変更しない。
- 既存amberlight-analytics WorkerのCron Triggerも毎時07/17/27/37/47/57分に確認する。GitHub scheduleの停止に依存しない起動経路。Worker自体はMetaへ送信しない。
- Workerはmainの同一コミットにある承認記事と台帳を読み、直近2日以内・鮮度有効・安全な未処理だけを検出する。対象があれば共通キューを起動。未処理がなければ最長30分間隔で読み取り監視を起動し、外部時計の動作もActionsに記録する。
- Cloudflare起動はrepository_dispatchイベント（固定のwork_signal_social_wakeup / work_signal_social_health）、監視による回収はmonitor_recoveryで識別できる。起動中・待機中・10分以内の重複要求は抑える。送信側の共通ロック、5記事上限、最大2回の進捗継続は維持。
- Workerの設定はSOCIAL_WAKEUP_ENABLED。既存EDITORIAL_PUBLISH_TOKENを固定のGitHubリポジトリのrepository_dispatch（既存のContents書き込み権限）に使用する。未設定・権限不足・取得不整合は停止し、成功扱いしない。新しいトークンや権限を自動作成しない。
- Instagramフィードの4/2207051保護停止は解除確認まで維持する。起動経路の追加は保護停止の解除や102件等の過去記事の一括再送を意味しない。
- API結果が不明なattempting/needs_reviewは人による実照合まで再送しない。投稿済み・未承認記事・恒久的な媒体除外を回収対象にしない。


既存の投稿承認・記事JSON・原稿ルールを維持。新しい必須入力はない。

## 配信の変更

- 記事の `social_publish:true` を配信依頼、永続台帳を媒体別の配信結果として扱う。Pagesの途中ビルドやSNS実行がキャンセルされても、依頼は記事データに残る。
- mainのPagesワークフロー成功を直接受け、直近2日以内・鮮度レビュー有効・承認済みの未処理記事を照合する。SEOだけの公開でも既存の配信待ちは回収するが、配信済み記事は再投稿しない。記事編集や媒体追加を新しい投稿承認とは扱わない。
- 定期起動は毎時06分・36分（UTC/JSTとも分は同じ）の30分間隔へ再設定した。1回5記事、公開・照合による進捗がある場合だけ最大2回続行する。続行できなくても未処理分は台帳と記事データから次回再計算する。
- すべての投稿は既存の共通ロック内で直列実行。待機中の実行も可能な限り保持する。送信前に実投稿をGET照合し、一致する既存投稿は送信せず台帳へ反映する。
- ストーリーズは空captionを未投稿と判定しない。画像比較・既知の公開画像との一致確認・当日記事という24時間以内の観測範囲が必要。確認できなければ保留。期限を過ぎた未処理記事は鮮度を再確認する。
- `attempting` / `needs_review` は自動再送しない。Instagramフィードの4/2207051保護停止も維持する。投稿数枠が空いたことだけで解除しない。
- 明示的な期限付き復旧レビューがある場合は、実投稿を再照合してからキューを選ぶ。通常の自動再送とは分離し、過去レビューは `.github/social-recovery-reviews/` とGit履歴へ保存する。10月31日の限定レビューはWordPress AI Engine記事のThreadsだけを対象とする。

## 投稿担当が継続すること

1. 一次情報・日時・内容・必要な媒体を確認し、ユーザー承認後、新記事へ `social_publish:true` を同じコミットで付ける。
2. `social_platforms` は恒久的な媒体選択。一時障害の回避のために媒体を削らない。過去記事へ承認フラグを一括付与しない。
3. 記事ID・初回公開日を固定する。SEO更新のためにIDを作り直したり、初回公開日を更新しない。
4. サイト公開、Threads、Instagramフィード、ストーリーズ、Xを別々に報告する。サイト公開成功や当該バッチ成功だけで「SNS全件完了」としない。
5. 全体の未処理はActionsの **Monitor WORK SIGNAL entire SNS backlog** と `social-backlog-status.json` で確認する。ready / deferred / needs_review / attempting / held / review_required を分けて確認する。監視は未処理・結果不明・鮮度切れで失敗する。定期実行90分超の空白はSCHEDULER_DELAYで別記する。フィード保護停止は別記する。

## Xは別の有効化手順

今回の安定化でXの認証・課金・配信は有効化しない。既存の媒体限定指定は維持する。Xを追加承認する新記事は `social_x_publish:true` を使える。開始基準より前の記事は自動補充しない。詳細は [X_AUTOPUBLISH.md](X_AUTOPUBLISH.md)。

## 制約と復旧

- Metaの保護制限、権限・認証エラー、GitHub全体の停止をコードだけで解消できるとは限らない。API結果が不明なら、重複を避けて停止する。
- 監視もGitHub Actions上で動くため、GitHubの起動自体がすべて止まった場合の外部死活監視は別途必要。定期実行時刻は配送時刻の保証ではない。
- 復旧対象は記事ID・媒体・一次情報の鮮度・実アカウントとの照合で限定する。臨時の固定記事用スクリプトは増やさない。台帳の削除・初期化、保護フラグの根拠のない解除をしない。

定期起動の停止原因は未確定。GitHub公式の再有効化手順に合わせてcron式を変更し、起動実績で確認する。設定変更だけを復旧完了とは扱わない。

## 2026-11-06: 所有者指定のInstagram一時停止

Instagram障害中はThreadsのみという所有者指定を、恒久的な記事ごとの媒体削除ではなく SOCIAL_PAUSED_PLATFORMS=instagram,instagram_story の運用停止として反映する。通常配信と全体監視のワークフローで同じ値を使う。

- 送信キューは一時停止した媒体を選ばず、フィード復旧プローブも実行しない。既存の投稿台帳・記事のsocial_platformsは維持する。
- 未送信/枠待ちの停止対象はレポートでpaused、全体監視ではheld/operator_pauseとして保持する。publishedには数えない。
- Threadsの未配信・結果不明・他のエラーは引き続き失敗にする。attempting/needs_reviewは停止設定で消さず、再送しない。
- Instagram再開は所有者判断で停止設定を外す。保護制限や履歴確認が解決した証拠を得るまでは外さない。解除だけで過去記事を一括再送せず、通常の鮮度・重複・台帳検証を適用する。
