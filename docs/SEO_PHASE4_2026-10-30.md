# WORK SIGNAL SEO追加改善（2026-10-30）

対象：検索登録の点検、検索実績に基づく既存記事の改善、テーマ別の入口、モバイル性能。

## 実装

- `/topics/` と、AIの業務活用・企業のセキュリティ対策・管理職の実務の3つの読む順番を静的HTMLで生成する。
- 基礎解説・事例・続報を編集指定で案内し、関連する公開記事を最大12件表示する。新しい記事は既存の公開条件を満たした場合だけ候補に入る。
- トップの記事一覧下部、フッター、該当する記事の既存サイドバーからテーマへリンク。検索・カテゴリー・フィルター・アーカイブを維持する。
- CollectionPage・ItemList・BreadcrumbList、固有title・description・canonical・OG/X情報を生成し、サイトマップに収録。
- テーマ本文の編集時は `scripts/topic_catalog.py` の `reviewed_at` を実際の確認日に更新。lastmodはガイドの確認日と表示記事の実際の更新日時から計算する。
- Fortinet、ASP.NET Core、React/Next.js、Claude Duet、Multerの5記事でtitle・summaryを改善し、既存の本文を保って末尾にFAQを追加。既存の見出しアンカーの順番は変えない。
- 記事ID・元の公開日・カテゴリー・スコア・一次情報URL・SNS承認と投稿文・台帳を保持。新規記事やSNS再投稿として扱わない。

## モバイル性能

Lighthouse 13.6.0のモバイル設定で公開トップ・JP Incident Monitor記事・SECURITY WATCH一覧を測定。PageSpeed Insights APIは共用枠の429で実行できなかったためGoogle公式のLighthouse CLIを使用。ラボ測定と実ユーザーのCore Web Vitalsは区別する。TBTはINPではなく、今回の測定から実ユーザーINPの合否は判定しない。

Google FontsのNoto Sans JPを、400/500/600/700/800/900の重複定義から可変ウェイト400..900へ変更。比較時点のCSSは697,741バイトから124,807バイトとなり、取得対象のフォントファイル129個は同一だった。書体・太さ・配色・アニメーションは削除しない。

市場パネルはURL設定前のリンクを非表示パネル内にも配置していた。URL確定後に同じリンクを挿入し、操作時の表示と参照先を維持する。

再測定例：

```sh
npx --yes lighthouse@13.6.0 https://signal.amberlight.co.jp/ --form-factor=mobile --only-categories=performance,seo,accessibility --chrome-flags="--headless=new" --output=json --output-path=/tmp/work-signal-mobile.json
```

スコアはネットワーク・端末・外部サービスで変動する。実ユーザーの値と、テストアクセスが混ざるGA4のPVを同じものとして扱わない。AdSense・GA4設定と親ドメインは変更しない。

## Search Console

検索結果への表示履歴、現在のインデックス登録状態、公開HTMLの技術的な状態を別々に管理する。検索実績はURL検査の結果ではない。

現在のGoogle登録状態・選択されたcanonical・最終クロールは、所有者認証のあるURL検査が必要。今回の接続では管理画面の操作やURL Inspection APIへの認証済み照会はできない。データに行がないURLを未登録と断定しない。

個別の検索実績や確認表は公開リポジトリに転載せず所有者向けの別資料で扱う。サイトマップは従来の `/sitemap.xml` を維持するため登録先変更は不要。

## 検証と公開

- Pythonテスト、旧共有URL、市場データ、NBAの既存テストを継続。
- テーマの公開条件・canonical・構造化データ・内部リンク・サイドバーを回帰テストに追加。
- 全記事・全テーマのHTMLとリンクを `python3 -m scripts.audit_seo_output` で確認。
- mainの最新変更を保持し必要なファイルだけを反映。Pagesのbuildとdeploy、および公開URLの本文を確認。
- ニュース収集・承認・SNS自動配信を変更しない。今回の改稿でSNS再投稿の承認を追加しない。
