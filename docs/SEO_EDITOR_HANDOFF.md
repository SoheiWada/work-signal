# WORK SIGNAL 投稿担当への共有｜SEO対応後の運用

2026-10-30（2026-10-22版を更新）

## 通常の投稿手順は継続

- 承認済み記事を、GitHubの最新 `data/articles.json` に既存記事を保持して追加する。
- JSONの既存形式・カテゴリー・採点・公開承認ルールは継続。新しい必須項目はない。
- 正式な記事URLは `https://signal.amberlight.co.jp/articles/<記事ID>/`。Threads等でもこのURLを使い、計測が必要なら従来のUTMを付ける。
- 公開後の `id` は固定。改稿で `published_at` を今日の日付に変えない。公開日とニュース元の発表日は別の情報として扱う。
- `summary` は記事固有の検索説明文にも使われる。本文の内容と一致する要約を書く。SEOのために事実や編集方針を変更しない。

## 自動化されること

- mainの更新で、記事別HTML・canonical・OGP・X向けメタ情報・Article/NewsArticle・共有画像・サイトマップを生成する。
- 記事ごとの実際の改稿履歴から、画面の更新日・dateModified・サイトマップlastmodを生成する。別の記事の追加、並び替え、採点変更、再公開処理では、無関係な記事の日付を更新しない。
- 通常は更新日を手入力する必要はない。必要に応じて任意の `updated_at` に `YYYY-MM-DD` またはタイムゾーン付きISO日時を指定できる。根拠のない日付は入力しない。
- 関連記事は既存サイドバー内に最大2件生成する。任意の `related_article_ids` に指定した順を優先し、指定先から戻るリンク候補も生成する。その後、同じCVE・製品・具体的なテーマで選ぶ。カテゴリーや「重大」「脆弱性」などの一般語の一致だけでは選ばない。非公開・既存の公開基準に満たない記事・存在しない記事・自分自身は対象外。
- 指定例：`"related_article_ids": ["既存の続報記事ID", "既存の基礎解説記事ID"]`。新しい必須項目ではなく、通常は省略できる。記事のURLではなく公開済み記事のIDを使う。機械的な相互リンクのために無関係な記事を指定しない。
- faviconを固定URLで自動生成する。投稿のたびに画像や設定を追加する必要はない。

## 公開確認

1. 既存のPythonテスト・市場データ／NBAテストを実行する。旧記事URLの検証には `node --test tests/seo/*.test.mjs` も使う。
2. `python3 scripts/build_site.py` を実行し、記事とサイトマップが生成されることを確認する。
3. mainへの反映後、GitHub Actionsのbuildとdeployの両方が成功したことを確認する。コミット成功だけでは公開完了にしない。
4. トップ、正規記事URL、必要に応じて旧共有URLで本文を確認する。
5. 新記事の追加ごとにSearch Consoleのサイトマップを再登録する必要はない。既存の `/sitemap.xml` が自動更新される。必要な代表記事だけURL検査を行う。

生成済み `_site/` を直接編集・コミットしない。完全なGit履歴を使う公開ビルドで更新日を判定するため、ZIP単体や浅いcheckoutの手元表示には更新日が出ない場合がある。

Googleへの登録・検索順位・サイト名・faviconの反映は即時ではない。新記事が未登録でも、公開失敗と決めつけず、Actions・公開URL・Search Consoleの順で確認する。

親ドメインのAdSense設定、DNS、GA4、デザイン、ニュース収集、Threads文末の一次情報URLのルールは継続。

## 既存記事の改善とThreads（2026-10-30）

- 検索表示がある記事を優先し、タイトルで対象製品・何が分かるかを明確にする。本文にない使い方・対策や、確証のない悪用をタイトルで約束しない。すべてのタイトルに同じ型を強制しない。
- セキュリティ記事は「対象・影響条件・影響バージョン／修正版・対応・悪用確認の有無・一次情報」を確認する。続報と別の脆弱性を区別し、現在の修正状況へつなぐ。
- 記事をSEO改稿しても、新記事として作り直さず、ID・元の公開日・SNS承認フラグ・媒体選択・既存投稿台帳を維持する。改稿はSNS再投稿の承認ではない。
- Threadsは読者の業務上の疑問から始め、記事で分かることを具体的に紹介する。検索キーワードの羅列や不安を過度にあおる表現を避ける。500字以内・記事URL入り・文末の一次情報URLは従来どおり。
- JP Incident Monitorは公開された事故情報を調べる入口。将来の侵入を予測する、事故を未然に検知する、Confidenceが正確さの確率を示す、とは書かない。
- Search Consoleは記事URLと検索語を分け、表示回数・クリック・CTR・掲載順位を同じ期間で比較する。GA4のセッション・エンゲージメントと検索クリック数は別の指標。エンゲージメント率を読了率と呼ばない。
- 効果確認はまず2〜4週間。検索流入、1セッション当たりの閲覧、記事からの次ページ閲覧を比較し、Threadsは投稿ごとのUTMで流入と反応を確認する。収益はAdSenseの実績で別途追跡する。

今回のSEO改稿はサイトへの反映のみ。Threadsへの新規投稿・再投稿は実行しない。
